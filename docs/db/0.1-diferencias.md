# 0.1 — Diferencias entre `database/` (legacy) y producción

Fuente: catálogo de producción (`dynshsoyjojfkdqdlsoy`, Postgres 17) leído con el MCP de Supabase el 2026-11-13, en modo solo lectura. Datos: 1.683 estaciones, 31 zonas, 247 precios y 22 reportes. Nunca hubo historial de migraciones; la primera registrada es el hotfix 0.0.

La verdad queda en `supabase/migrations/20261113000000_baseline.sql`.

## Columnas y constraints

| Objeto | Legacy (`schema.sql` y parches) | Producción | Acción |
|---|---|---|---|
| `fuel_prices.price` | `DECIMAL(6,3)`, `CHECK (price > 0 AND price < 100)` | `numeric(10,2)`, `CHECK (price > 0 AND price < 100000)` | Ningún script del repo hace este cambio: se hizo a mano. La baseline toma producción. En la 1.3 el rango pasa a `fuel_price_ranges` |
| `fuel_prices.currency` | Default `'USD'` | Default `'USD'`, pero las 247 filas son `COP` | Migración futura: default `'COP'` o quitar la columna (siempre es COP) |
| `fuel_prices.fuel_type` | `schema.sql` permite `super` y no `corriente` ni `gnv` | `extra, corriente, diesel, urea, gnv` (por `gnv_migration.sql`) | Sin acción |
| `fuel_prices.expires_at` | Default `now() + 24h` | Igual | Lo resuelve la 2.1 (frescura) |
| `fuel_prices.price_unit` | Solo en `gnv_migration.sql` | `varchar(10)`, `gallon`/`m3` | Sin acción |
| `stations.osm_id` | Índice único parcial (`migration_seed.sql`) o constraint `UNIQUE` (seed) | Constraint `UNIQUE (osm_id)` (ganó el seed) | Sin acción |
| `stations.has_gnv` y `svc_*` | Parches sueltos | Presentes | Sin acción |
| `zones.name` | Sin unicidad | Constraint `zones_name_unique` (no está en ningún script del repo) | Sin acción. La baseline la incluye |
| `zones.city`, `dept` y `code` | `migration_seed.sql` | Presentes, más un índice único parcial en `code` | Sin acción |

## RLS y permisos

| Tabla | Producción | Riesgo | Tarea |
|---|---|---|---|
| `stations` | Solo SELECT público desde el hotfix 0.0; sin INSERT, UPDATE ni DELETE para `anon`/`authenticated` | Cerrado | 0.0 ✅ |
| `fuel_prices` | INSERT público (`true`) y UPDATE público (`true`) | Cualquiera inserta precios sin límite y cambia precios o votos ajenos | 1.2 / 1.3 |
| `reports` | INSERT público y UPDATE público | Igual: spam y votos manipulables | 1.2 / 1.3 |
| Todas las tablas | `anon`/`authenticated` conservan TRUNCATE, REFERENCES y TRIGGER (grants por defecto de Supabase) | TRUNCATE salta la RLS. La API REST no lo expone, pero conviene quitarlo como defensa en profundidad | 1.3: `REVOKE TRUNCATE` |
| `spatial_ref_sys` | Sin RLS (advisor crítico) | Es de PostGIS y vive en `public` porque la extensión está ahí. No se puede mover con `ALTER EXTENSION ... SET SCHEMA` | Documentado. Revisar con soporte de Supabase si vale la pena |

## Funciones, triggers y vistas

| Objeto | Producción | Observación |
|---|---|---|
| `get_zone_averages()` | `SECURITY DEFINER`, sin `search_path`, devuelve `avg_corriente` y `avg_gnv` | El `schema.sql` legacy devolvía `avg_super`. Hay que fijarle `search_path` (advisor) |
| `refresh_latest_prices()` y `refresh_daily_avg_prices()` | Funciones trigger `SECURITY DEFINER` sin `search_path`, `REFRESH ... CONCURRENTLY` por cada INSERT (FOR EACH STATEMENT) | Por `/rpc` no se pueden llamar: Postgres rechaza las funciones trigger fuera de un trigger. El costo es el refresh completo por cada reporte. Lo cambia la 2.3 a pg_cron |
| `mark_station_has_gnv()` | `SECURITY DEFINER` y, desde el hotfix 0.0, con `search_path=public` | ✅ |
| `sync_station_location()` | Invoker, sin `search_path` | Advisor WARN, bajo riesgo |
| `v_station_summary` | Vista con permisos del dueño (advisor ERROR: security definer view) | Expone por la API un resumen que salta la RLS. Hoy solo lee datos públicos; pasarla a `security_invoker = on` |
| `latest_prices` y `daily_avg_prices` | Vistas materializadas legibles por `anon` (advisor WARN) | Son datos públicos a propósito, se aceptan |

## Realtime

La publicación `supabase_realtime` **no tiene ninguna tabla**. El frontend (`stations.service.js`) se suscribe a `postgres_changes` de `fuel_prices`, `reports` y `stations`, pero **en producción nunca le llega un evento**: el "tiempo real" no funciona y la app solo se actualiza al recargar.

No se activa todavía. Con el código actual, cada evento haría un refetch completo de todas las estaciones. Se activa en la 0.4, cuando el realtime parchee la caché (`ALTER PUBLICATION supabase_realtime ADD TABLE ...` en una migración).

## Extensiones

`postgis` 3.3.7 en `public` (advisor WARN), y `uuid-ossp` y `pgcrypto` en `extensions`. `pg_cron` y `pgtap` no están instaladas: la 2.3 necesita `pg_cron` y la 0.2 necesita `pgtap` solo en local.

## Pendiente de validar

La baseline se armó desde el catálogo y no con `pg_dump`. Hay que verificar que en una base vacía quede igual a producción:

```bash
npx supabase start          # requiere Docker
npx supabase db reset       # aplica baseline + hotfix en local
npx supabase db diff --linked   # debe salir vacío
```
